# v1.0.0-rc.5

### Relations declared with `defineRelations` are now used for seeding

`drizzle-seed` fills a foreign key column with a value that exists in the table it points at. Until now it could only
learn about those links from foreign key constraints; it now picks them up from relations declared with
`defineRelations` as well, which makes seeding work on schemas that have no foreign keys in the database at all.

A database created with its relations already carries them, so nothing has to be passed to `seed`:

```ts
import { drizzle } from "drizzle-orm/node-postgres";
import { seed } from "drizzle-seed";
import * as schema from "./schema.ts";
import { relations } from "./relations.ts";

const db = drizzle(process.env.DATABASE_URL!, { relations });

await seed(db, schema);
```

Relations can also be handed to `seed` directly, which takes precedence over the ones the database was built with:

```ts
await seed(db, schema, { relations });
```

Many-to-many relations declared with `.through()` are followed too: the junction table is filled with rows that
reference both of the tables it joins.

```ts
export const relations = defineRelations(schema, (r) => ({
  users: {
    groups: r.many.groups({
      from: r.users.id.through(r.usersToGroups.userId),
      to: r.groups.id.through(r.usersToGroups.groupId),
    }),
  },
}));
```

`defineRelations` does not record which side of a relation holds the foreign key, so when no foreign key constraint
backs it, the direction is inferred: the side whose columns are a primary key or a unique constraint is the one being
referenced. A relation that cannot be seeded is skipped rather than guessed at; one joining two columns that are a
key on neither side, one whose child column is already filled by another relation, and one whose every orientation
would close a not-null reference cycle.

### `dryRun` generates the data without writing it

`dryRun()` runs the whole generation and hands back the result instead of writing it. No query is issued: the database
is only used to tell which dialect to generate for.

```ts
const data = await seed(db, schema, { count: 5 }).dryRun();

data.users; // [{ id: 1, name: "Melanie" }, ...]
data.posts; // [{ id: 1, ownerId: 1, title: "..." }, ...]
```

The rows are exactly the ones a real `seed` with the same `seed` number would have written, relations included, keyed
by the names the tables have in the schema object and typed as `InferInsertModel` of each table. `refine` works the
same way:

```ts
const data = await seed(db, schema)
  .refine((funcs) => ({
    users: { count: 3, columns: { name: funcs.firstName() } },
  }))
  .dryRun();
```

### `dryRun({ output: "sql" })` the seed as SQL statements

`output: "sql"` gives back the statements a seed would run, with their values written into them, so a seed can be
saved and replayed anywhere:

```ts
const statements = await seed(db, schema, { count: 5 }).dryRun({ output: "sql" });

// [`insert into "users" ("id", "name") values (1, 'Melanie'), (2, 'Kurt')`, ...]

fs.writeFileSync("seed.sql", statements.join(";\n") + ";");
```

### A dry run can be streamed instead of awaited

Both forms of `dryRun` are async iterable. Iterating never holds more than one batch in memory, so it scales to seeds
far larger than memory:

```ts
import fs from "node:fs";

fs.writeFileSync("seed.sql", "");

for await (const statement of seed(db, schema, { count: 1_000_000 }).dryRun({ output: "sql" })) {
  fs.appendFileSync("seed.sql", statement + ";\n");
}
```

### `refine` is now chainable

`refine` returns the seed itself rather than a promise, so it composes with `dryRun`:

```ts
await seed(db, schema).refine((f) => ({ users: { count: 3 } }));            // still seeds, as before
await seed(db, schema).refine((f) => ({ users: { count: 3 } })).dryRun();   // generates without writing
```

### Composite primary keys are seeded as the unique keys they are

A table level `primaryKey({ columns: [...] })` is now generated as a composite unique key, so a junction table gets
distinct pairs even though neither of its columns is unique on its own:

```ts
const usersToGroups = pgTable("users_to_groups", {
  userId: integer("user_id").notNull().references(() => users.id),
  groupId: integer("group_id").notNull().references(() => groups.id),
}, (t) => [primaryKey({ columns: [t.userId, t.groupId] })]);

await seed(db, schema, { count: 5 }).refine(() => ({
  usersToGroups: { count: 20 }, // 20 distinct (userId, groupId) pairs
}));
```

## Improvements

- Seeding no longer keeps every generated row in memory. Rows are generated batch by batch, and a table's rows are
  dropped as soon as no table still waiting to be seeded references them, so memory follows the shape of the schema
  instead of `count`.
- `with` now warns when it is asked for a number of rows per parent row on a column that is part of a composite unique
  key, where the count cannot be honoured, instead of silently ignoring it.

## Bug Fixes

- PostgreSQL sequence synchronisation now only runs for columns that actually have a sequence behind them — `serial`,
  identity, or an explicit `nextval` default. Plain integer columns written with explicit values are no longer passed
  to `setval`.
- Tables that share a database name in different database schemas are now told apart, so their relations and column
  name maps no longer overwrite each other.
- Two relations between the same pair of tables are both kept, instead of the first one standing in for the second when
  deciding which relations are cyclic.
