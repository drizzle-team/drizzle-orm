# Snapshots carry a state hash, and each format has its own replay module

The replay logic is part of the snapshot format. A code change that alters how an existing snapshot rebuilds would give a wrong state with no error. From snapshot format 9 on, every snapshot stores a hash of its state, and a rebuild that reaches another state fails and names the snapshot. The replay for a format lives in its own module, which imports no dialect rules.

## Consequences

- `generate` replays the new deltas on the parent state before it writes a snapshot. It refuses to write when the result differs from the state that the diff used. The hash does not catch a wrong snapshot at write time, because the same run computes it.
- `check` rebuilds every leaf once and compares its hash, so a wrong rebuild fails in CI and not at the next `generate`. `check` still takes its conflicts only from the stored statements.
- The hash leaves out null fields, so a new optional field on an entity does not change old hashes. It sorts by code unit order, because a locale-aware sort gives another order on some machines.
- An intended change to the replay becomes a new format with a new module. `up` rebuilds old folders with the old module.
- The key functions are part of the format too. In a test, a changed key function made a rebuild lose rows with no error, and the hash is the guard that catches this.
- A history test runs committed histories, merges included, on PGlite and compares the database with the rebuilt state. A committed expected file can be regenerated by the same wrong logic, and a database cannot.
