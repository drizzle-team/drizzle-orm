# A rename is one delta, and reconstruct applies its effects through the edges

From snapshot format 9 on, a migrations folder holds one base snapshot. It is the first snapshot of the folder, and it holds the full schema state. Every other snapshot is a diff snapshot, which holds the deltas of its own migration: one create, drop, alter or rename for each changed entity. A delta names the entity by the key of that entity. A rename also changes the entities that reference the renamed entity, such as the columns of a renamed table, and the snapshot stores nothing for those entities. Reconstruct applies every delta through a call to the DDL engine, which is the store of entities in `src/dialects/dialect.ts` that the diff uses too. For a rename, the `update` function of the engine follows the edges and writes the new name into the referencing entities. The team chose this design because the engine already applies a rename in this way for the diff. The instructions of ADR 0003 were a second mechanism for the same effects, and that mechanism had its own code.

Every snapshot also stores the statements of its migration, and ADR 0002 stays valid. One reason in ADR 0002 no longer applies: a base snapshot is never inside a branch, because a folder holds only one base snapshot. A base snapshot keeps its statements. This record replaces ADR 0001 and ADR 0003. Both rejected this design, because a later change to the edges might change the state that an existing snapshot reconstructs to. ADR 0006 accepts that risk. Only postgres has format 9.

## Considered options

- Instructions (ADR 0003). A snapshot stored the effects of a rename as instructions. An instruction selected entities by what those entities reference. Reconstruct did not read the edges, so a later change to the edges did not change how an existing snapshot reconstructs. The instructions needed a handler that applies them and a rule that derives them from the edges. In that rule, the condition of an edge could read only the fields that the edge maps.
- A drop that follows the edges too. A dropped table would be one drop delta, and the engine would remove its columns, constraints and indexes. A schema file cannot reference a dropped entity, so the diff already finds every removed entity and stores a drop for each one. An index that keeps its other columns after a column drop must stay in the state in a changed form, and a drop that follows the edges can only remove the index.
- Full state in every snapshot (format 8). Each snapshot repeats the whole schema.
- Stored effects with key translation, and stable ids. ADR 0003 describes both.

## Consequences

- The commands that read the folder refuse a folder with a second base snapshot. Two git branches that each start from an empty folder both write a base snapshot, so the second base snapshot appears only after a git merge. The error names both migration folders, and it tells the user to delete one of them and to run `generate` again. `up` refuses an older folder with two first migrations in the same way.
- A create, a drop and an alter change one entity. Only a rename follows the edges.
- `ddlDiff` records one rename delta for each rename decision when it applies that decision to the old state. The final comparison of the two states supplies the creates, drops and alters. A check in the test helpers applies the deltas of every diff and compares the result with the new state, because a change to the old state that bypasses `update` would go unrecorded.
- One set of rules covers a delta that does not fit the state, in a merge and outside a merge. Reconstruct skips a drop, an alter or a rename of a missing entity, and a skipped rename has no effects on other entities. A create onto a taken key does nothing when the entity at that key is equal, and it throws when that entity differs. A rename that moves an entity onto a taken key throws.
- A merge needs the skip. Some changes store a delta and no statement, such as a NOT NULL change of a primary key column. `check` compares only statements (ADR 0002), so it finds no conflict between such a change and a table rename on another branch. If reconstruct applies the rename first, the delta names an entity that is missing under the old key, and reconstruct skips that delta. The diff for the merge snapshot then finds the change again, because that diff compares the schema with the combined state.
- Outside a merge, a delta that does not fit exists only after a hand edit, a drift (ADR 0006) or a bug in the diff. Reconstruct skips such a delta there too, so that one set of rules covers both cases.
- A merge snapshot stores only its own deltas, relative to its combined state. The combined state is the state of the first parent of the merge snapshot, plus the deltas of the rest of the merge's history, applied in folder-name order. The first parent is the leaf with the newest folder name. Existing merge snapshots depend on this rule, and a change to the rule would change the state that those snapshots reconstruct to.
- A folder name must sort after the names of its parents, because the migrator runs migrations in folder-name order, and reconstruct applies the rest of a merge's history in that order. `generate` names new folders to keep that rule, and the commands that read the folder check it.
- A rename of one branch reaches the entities that the state holds when reconstruct applies the rename, so the rename also reaches entities that the first parent added. In a trial on random histories with merges, a prototype of this design and the instructions gave the same states for every history that `check` accepts. The two differed only for merges that `check` rejects. The prototype replaced the entity at a taken key, so the trial did not cover the create that throws.
- A delta names an entity by the names that the SQL for that change uses. An index is therefore keyed by schema and name, because `DROP INDEX` and `ALTER INDEX RENAME` do not name the table. With the table in the key, a table rename on one branch made the index delta of the other branch miss the index.
- `up` refuses an old merge whose branches gave one key to two different entities, through a rename or through two creates.
- The engine reaches a referencing entity only through the referenced entity. drizzle-kit does not support an entity that a schema file uses and does not export, so the state always holds every referenced entity, and no code handles the other case. With an unexported entity, a rename of its database schema leaves the old schema name in the entities that reference the unexported entity, and the diff of the same migration writes SQL for those entities.
- Reconstruct costs more than it did with instructions, because one rename reads every entity of the state. In a trial, a history with 500 renames and a state of 5500 entities took 2.5 to 4 s, and it took less than 0.1 s with instructions. `update` therefore gets two changes, which the trial did not have. It copies all entities, to put them back after a key conflict, only when a key changes. A caller can also name one entity by its key, so that `update` does not search the state. Every dialect runs `update`, so these changes reach all dialects.
- The order of the entities in a reconstructed state is not guaranteed.
- The format number stays 9 after this change to the stored shape of a snapshot. No released version wrote a format 9 snapshot, so no converter reads a snapshot that stores instructions.
