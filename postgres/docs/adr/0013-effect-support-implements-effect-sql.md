# Effect support implements `effect/sql` over the Drizzle Postgres pool

Effect 4 ships its own Postgres client, `@effect/sql-pg`. Drizzle Postgres still offers Effect support, so that Effect applications that use the `sql` template, and Drizzle users of `effect-postgres`, can run on Drizzle Postgres. The support implements Effect's `SqlClient` contract (`SqlConnection.Connection`) on top of the existing `Pool` and `Connection`. Spans, transactions, savepoints and typed errors then come from Effect core. Drizzle Postgres does not get its own Effect-only query API, and its protocol layer is not rewritten in Effect.

The entry point follows the pattern of Effect's own drivers. It has its own `DrizzlePostgresClient` service, which extends `SqlClient` with Drizzle Postgres's extras, and its layers provide both `DrizzlePostgresClient` and `SqlClient`. The layer config uses Effect's names and types (`username`, `Redacted` passwords, `Duration` timeouts), and `client.json`, `DrizzlePostgresClient.layerConfig`, `layerFrom` and `fromPool` match their `PgClient` counterparts. Code written against `SqlClient` then moves from `@effect/sql-pg` by swapping one layer. Code written against `PgClient` does not move, because Drizzle Postgres has no `listen` or `notify`.

The pools dial through a `DrizzlePostgresTransport` service in context, in the same way as `FetchHttpClient.layer` provides Effect's `HttpClient`. The async entry point registers the Node transport for the whole process when it is imported. The Effect entry point does not use that registration, so its transport stays local to each pool. The runtime entries provide their transport inside `DrizzlePostgresClient.layer`, `layerConfig` and `make`, so the common case needs no extra layer. Only `./effect/core` requires `DrizzlePostgresTransport` in the layer's type, in the same way as the root `./core` requires a `transport` or `socket`. Each runtime entry also exports its transport as `DrizzlePostgresTransport.layer`, which combines with the core client. The transport also carries the cancel request, which gives the Cloudflare and Deno pools a server-side cancel as well.

Its subpaths mirror the async entry point one to one. `@drizzle-team/postgres/effect` picks its entry with the same export conditions as the package root: `workerd` resolves to `./effect/cf`, `deno` to `./effect/deno`, and `node` and `bun` to the Node entry. Every runtime entry exports `DrizzlePostgresClient` and `DrizzlePostgresTransport` under the same names and types, so one line of code works on every runtime. Like the root, it has no fallback, so a target without TCP fails at build time. `./effect/node`, `./effect/cf` and `./effect/deno` force a runtime, and `./effect/core` takes a transport layer, a custom transport through `Layer.succeed(DrizzlePostgresTransport.DrizzlePostgresTransport, transport)`, or a pool from another entry point, such as `./neon-ws`. Effect's own packages split runtimes into separate packages, such as `@effect/platform-node` and `@effect/platform-bun`. Drizzle Postgres is one package, so it follows its own root entry instead. `effect` is an optional peer dependency with the range `~4.0.5`, because Effect marks its SQL modules as unstable, which allows breaking changes in minor releases. The core package keeps zero runtime dependencies.

Drizzle reaches it through its own module, `drizzle-orm/effect-postgres`, in the same way as its other Effect driver modules. Drizzle Postgres does not imitate the `PgClient` service of `@effect/sql-pg`, so Drizzle's `effect-postgres` module stays tied to the official client.

## Consequences

- Interrupting a query that waits behind another query in an explicit pipeline does not stop it. The server still runs it, and it commits. Only the query at the head of the pipeline gets a cancel request. This is documented on `pipeline`.
- Inside a transaction, an interrupt rolls the whole transaction back, so a query that still ran leaves no writes.
- The pool keeps its own reconnect. All fibers share one recovery after a lost connection, and a user's `Effect.retry` is an outer layer on top of it.
- The layer config has no `plugins` field, because Effect core already creates a span per statement. A pool passed in from outside keeps its own plugins, which gives two spans per query.
